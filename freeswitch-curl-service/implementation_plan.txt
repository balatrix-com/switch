# Security Remediation Plan: billing-switch & bswitchsub Integration

This plan addresses the vulnerabilities identified in the Cloudflare security audit report for [billing-switch](file:///d:/bala_billing/b-switch/billing-switch), taking into account the recent git pull changes (specifically commits `df2b7f9` and `8ec5e33` affecting machine-to-machine wallet operations and DID activations with [bswitchsub](file:///d:/bala_billing/b-switch/bswitchsub)).

## User Review Required

> [!IMPORTANT]
> **Recent Git Pull Impact (`df2b7f9`):** 
> The recent commit added `@Public()` and `@UseGuards(ApiKeyAuthGuard)` to `creditMinutes` and `debitOtc` in [wallet.controller.ts](file:///d:/bala_billing/b-switch/billing-switch/backend/src/wallet/wallet.controller.ts) to let `bswitchsub` call them.
> However, [api-key.guard.ts](file:///d:/bala_billing/b-switch/billing-switch/backend/src/common/guards/api-key.guard.ts) currently defaults to **allowing all requests** if `SWITCH_API_KEY` is not set in `.env` (`if (!expectedKey) return true;`). This must be fixed to fail closed, otherwise anyone can call debit/credit endpoints without an API key.

> [!WARNING]
> **Customer Self-Service vs Admin Boundaries:**
> 1. `WalletController.getAllWallets` and `topUpWallet` must be restricted to `Role.SUPER_ADMIN`.
> 2. For `PlansController` proxying to `bswitchsub`: `list` and `findOne` should remain accessible to customers, but `create`, `update`, and `remove` must require `Role.SUPER_ADMIN`. In `subscribe`, `customer_id` must match the authenticated JWT's customer ID unless the caller is `Role.SUPER_ADMIN`.
> 3. `WalletsController` and `NumberAssigningController` under `backend/src/subscription/` must be locked down to `Role.SUPER_ADMIN`.

---

## Proposed Changes

### 1. Hardening API Key Guard & Machine-to-Machine Auth

#### [MODIFY] [api-key.guard.ts](file:///d:/bala_billing/b-switch/billing-switch/backend/src/common/guards/api-key.guard.ts)
- **Problem:** When `SWITCH_API_KEY` is undefined or blank, the guard allows all requests (`return true`).
- **Fix:** Fail closed. Throw `UnauthorizedException` or `ServiceUnavailableException` if `SWITCH_API_KEY` is missing or not configured.
- Use constant-time buffer comparison (`crypto.timingSafeEqual`) instead of `===` to prevent timing attacks (matching the pattern already used in `subscription-did-token.guard.ts`).

---

### 2. Main Wallet Controller Access Control

#### [MODIFY] [wallet.controller.ts](file:///d:/bala_billing/b-switch/billing-switch/backend/src/wallet/wallet.controller.ts)
- **Problem:** `getAllWallets`, `getWallet`, and `topUpWallet` have no role guards. Any authenticated customer can see all tenant wallets and top up arbitrary amounts on any wallet.
- **Fix:** 
  - Add `@Roles(Role.SUPER_ADMIN)` to `getAllWallets` and `topUpWallet`.
  - On `getWallet` and `getTransactions`, allow `SUPER_ADMIN`, or ensure `customerId === req.user.customerId` if the caller is a `CUSTOMER`.

---

### 3. Subscription Proxy to bswitchsub

#### [MODIFY] [plans.controller.ts](file:///d:/bala_billing/b-switch/billing-switch/backend/src/subscription/plans.controller.ts)
- **Problem:** Any logged-in customer can create, edit, or delete plan catalogs in `bswitchsub`, or subscribe other customer IDs bypassing balance checks.
- **Fix:**
  - Add `@Roles(Role.SUPER_ADMIN)` to `create`, `update`, and `remove`.
  - In `subscribe`, enforce that non-super-admins cannot set `override_balance_check: true` and cannot pass a `customer_id` different from their own token.

#### [MODIFY] [wallets.controller.ts](file:///d:/bala_billing/b-switch/billing-switch/backend/src/subscription/wallets.controller.ts)
- **Problem:** Exposes arbitrary-customer balance adjustments (`PATCH /wallets/:customer_id`), quota deductions (`POST /wallets/deduct`), and number asset assignments without role verification.
- **Fix:**
  - Add `@Roles(Role.SUPER_ADMIN)` across `WalletsController` and `NumberAssigningController`.

---

### 4. SIP Digest Identity Spoofing (Kamailio)

#### [MODIFY] [kamailio.cfg](file:///d:/bala_billing/b-switch/billing-switch/kamailio/kamailio.cfg)
- **Problem:** Line 310 forwards `$fU` (caller-provided SIP From URI user) in header `X-SIP-User`. An extension can authenticate with their own credentials but send another extension's username in the From header, routing and billing outbound calls under that other account.
- **Fix:** Capture the digest-authenticated username (`$var(auth_user) = $au;`) immediately following `proxy_authorize()`, and append `X-SIP-User: $var(auth_user)`.

---

### 5. XML Attribute Injection (FreeSWITCH Route Server)

#### [MODIFY] [route_server.py](file:///d:/bala_billing/b-switch/billing-switch/freeswitch-curl-service/route_server.py)
- **Problem:** Raw f-strings interpolate customer normalization output (`egress_number`) and caller ID into dialplan XML attributes (`action data="..."`). Quotes and XML markup in these fields can break out of attributes and inject arbitrary FreeSWITCH `<action>` tags.
- **Fix:**
  - Import `xml.sax.saxutils.quoteattr`.
  - Sanitize and escape all customer-controlled attributes (`egress_number`, `caller_id_number`) before constructing FreeSWITCH dialplan XML.
  - Validate that `egress_number` adheres to strict dialable phone number patterns (e.g. `^\+?[0-9]{3,32}$`).

## Verification Plan

### Automated / Unit Tests
- Run `npm test` in `backend/` to ensure no regression in existing auth and did-activation suites.
- Test `ApiKeyAuthGuard`:
  - Request with no `SWITCH_API_KEY` configured in environment -> Expect 503 / 401.
  - Request with invalid `x-api-key` header -> Expect 401 Unauthorized.
  - Request with valid `x-api-key` -> Expect 200/201.

### API Isolation Verification
1. Log in with a `CUSTOMER` JWT:
   - `GET /api/v1/billing/wallets` -> Expect `403 Forbidden`.
   - `PATCH /api/v1/billing/wallets/:otherCustomerId` -> Expect `403 Forbidden`.
   - `POST /api/v1/plans` -> Expect `403 Forbidden`.
   - `PATCH /api/v1/wallets/:otherCustomerId` -> Expect `403 Forbidden`.
2. XML injection validation:
   - Pass test strings containing `"><action application="hangup"/>` into normalization profiles and confirm generated XML contains `&quot;&gt;&lt;action` within data attribute rather than a new XML element node.
