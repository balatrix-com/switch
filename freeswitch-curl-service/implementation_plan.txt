# Multi-Tenant Architecture & Customer Portal Implementation Plan

This plan outlines the end-to-end transformation of `billing-switch` from a single-role administrative application into a **multi-tenant system** with **Super Admin** and **Customer (Tenant User)** access levels, JWT-based authentication, strict backend tenant isolation, role-based frontend routing, and a clean customer creation workflow.

As requested, this implementation builds on patterns from the reference project [pbx-whitelable](file:///d:/bala_billing/wlabel/pbx-whitelable) while adapting cleanly to `billing-switch`'s architecture without legacy migration overhead.

---

## User Review Required

> [!IMPORTANT]
> **Development Reset & Customer Data Cleanup**:
> As instructed, existing development customers will not be migrated. A cleanup script will remove the current 14 development customer records and their dependent rows (numbers, routes, settings, XML, SIP traces) and un-assign inventory numbers back to `AVAILABLE`. System-level data (**Carriers**, **Carrier Endpoints/Routes**, **Rate Cards**, **Number Inventory pool**, and **Global Normalization Profiles**) will remain untouched. A default Super Admin account (`admin@switchboard.local` / `Admin@123456`) will be seeded.

> [!IMPORTANT]
> **Strict Backend Tenant Isolation (`@CustomerId()`)**:
> In the current codebase, `@CustomerId()` blindly trusts the `X-Customer-ID` HTTP header. Under the new architecture:
> - For **Customer** users: `@CustomerId()` strictly reads `user.customerId` directly from the authenticated JWT session. Any header, body, or query param containing a different customer ID is ignored and blocked.
> - For **Super Admin** users: `@CustomerId()` allows inspecting or managing any tenant via route param `:customerId`, query `?customerId=...`, or header `X-Customer-ID`.
> This guarantees cross-tenant access is impossible via URL manipulation, header spoofing, or API forgery.

## Architecture Comparison & Target Design

### 1. Current State (`billing-switch`)
- **Authentication**: None. Direct unrestricted API access.
- **Tenant Context**: Frontend manually injects `X-Customer-ID: <id>` on requests; backend parameter decorator reads header without verifying identity.
- **Frontend UI**: Single layout with Super Admin menus. Customer configuration only accessible under `/management/customers/:customerId/*`.
- **Authorization**: Flat access. Anyone can query or modify any customer by modifying the URL or headers.

### 2. Reference State (`pbx-whitelable`)
- **Authentication**: JWT access tokens + refresh tokens, bcrypt password hashing, Passport JWT strategy.
- **RBAC**: `Role` enum (`SUPER_ADMIN`, `ADMIN`, `SUPPORT`).
- **Tenant Context**: JWT payload contains `{ sub, email, role, tenantId }`. Controllers use `targetTenantId = user.role === 'SUPER_ADMIN' && paramTenant ? paramTenant : user.tenantId`.
- **Frontend**: Protected routes using `ProtectedRoute`, `AuthProvider` context, role-based sidebar menus, separate Super Admin dashboard (`/platform`) vs Customer dashboard (`/dashboard`).

### 3. Target State for `billing-switch`

## Proposed Changes

### Component 1: Database & Prisma Schema

#### [MODIFY] [schema.prisma](file:///d:/bala_billing/billing-switch/backend/prisma/schema.prisma)
1. Add `Role` enum:
   ```prisma
   enum Role {
     SUPER_ADMIN
     CUSTOMER
   }
   ```
2. Add `UserStatus` enum:
   ```prisma
   enum UserStatus {
     ACTIVE
     SUSPENDED
     DELETED
   }
   ```
3. Add `User` model:
   ```prisma
   model User {
     id           String     @id @default(uuid())
     email        String     @unique
     passwordHash String     @map("password_hash")
     name         String?
     role         Role       @default(CUSTOMER)
     status       UserStatus @default(ACTIVE)
     customerId   String?    @map("customer_id")
     createdAt    DateTime   @default(now()) @map("created_at")
     updatedAt    DateTime   @updatedAt @map("updated_at")

     customer     Customer?  @relation(fields: [customerId], references: [id], onDelete: Cascade)

     @@index([customerId])
     @@index([role])
     @@index([email])
     @@map("users")
   }
   ```
4. Add relation field `users User[]` to `Customer` model.

#### [MODIFY] [customer-id.decorator.ts](file:///d:/bala_billing/billing-switch/backend/src/common/decorators/customer-id.decorator.ts)
- **Refactor to enforce tenant isolation**:
  ```typescript
  export const CustomerId = createParamDecorator(
    (options: CustomerIdOptions | undefined, context: ExecutionContext) => {
      const req = context.switchToHttp().getRequest();
      const user = req.user; // Set by JwtStrategy

      // 1. If user is a Customer, tenant ID MUST come from their verified session
      if (user && user.role === Role.CUSTOMER) {
        if (!user.customerId) {
          throw new ForbiddenException('User is not associated with an active tenant');
        }
        return user.customerId;
      }

      // 2. If user is Super Admin, allow scoping by param, query, or header
      if (user && user.role === Role.SUPER_ADMIN) {
        const fromParam = req.params?.customerId;
        const fromQuery = req.query?.customerId;
        const fromHeader = req.headers['x-customer-id'];
        const resolved = fromParam || fromQuery || fromHeader;
        if (resolved) return String(resolved);
        if (options?.required === false) return undefined;
        throw new BadRequestException('customerId must be specified for administrative action');
      }

      // Fallback for internal / legacy callers if unauthenticated
      ...
    }
  );
  ```
